Overview — the data landscape

Two SQL Server databases:

DatabaseRoleHolds
claimtoolkit_united (per-customer, 282 tables)The customer's live claim dataClaims, parties, facts, assessment, investigation, audit, checklist, Ask CTK prompts, auth
claimtoolkit (shared/central, 201 tables)Cross-customer reference & platformCompliance (state-law) content, Total Loss rules, company registry & billing, CTK products/config

Plus four non-SQL stores: Redis (login session context + cached lookups — used by the web backend and the mobile API), PostgreSQL (AI apps — chat, memory, feedback), AWS S3 (scene images, evidence, identity, transcripts, PDFs), and a local FAISS vector index (compliance search). AWS Textract provides identity-document OCR.

Multi-tenant — one central DB + N per-customer replicas: the .NET APIs connect to the master Claimtoolkit DB, look up the company's DatabaseName, format the TenantDbTemplate ({db} placeholder), then work against that customer's own DB. claimtoolkit_united is just one customer replica — elcl, united-uat, etc. each have an identical 282-table copy. ToolkitID is the master claim key stitching every table together; ClaimID, AutoPartyID, AutoInvestigatorID, AssessmentID are the secondary joins.

Deployment model & where each application's data lives

One central database + one replica per customer. There is no single "United database" — every customer/client gets its own copy of the same claim schema (the prod dump claimtoolkit_united is just United's copy; elcl, united-uat, … are siblings). The central Claimtoolkit DB is shared by all of them and holds the registry that tells the .NET APIs which customer DB to open.

How a request finds its data: MainDb (master/ACL) → look up the company's DatabaseName → format TenantDbTemplate (replace {db}) → open that customer's SQL DB. Scene API uses ClaimtoolkitAutoConnection; Mobile API uses ClaimtoolkitConnection → company connection.

Are Compliance and Audit in the same DB as claims? No — they sit on opposite sides of the split. Verified by counting CREATE TABLE statements in each prod dump:

Which app reads which: AI-CTK-NLP points at the central DB (DATABASE_NAME = "ClaimtoolKit") to pull compliance content; the Legacy ASP compliance pages read the same DB* tables; the Auto Liability / Mobile / Scene APIs read/write the per-customer replica. So Compliance content and the core claim tables coexist in the central DB, and Audit coexists with claims in each customer replica — the layout is shared-vs-per-customer, not one-database-per-application.
🔎 For the AI-for-Audit work: the RFP referred to a separate ClaimToolkit_Audit database, but the current prod schema has no separate audit DB — the 145 audit tables are embedded inside each customer replica alongside the claim tables. Carry this correction into that design.

Key insights

1. ToolkitID is the spine. Claim, parties, facts, assessment, investigation, scene, files, audit, disposition — all carry it. It's the join key for any cross-table or AI query.

2. Two-database split: claimtoolkit_united = the customer's live claim/investigation/audit data; claimtoolkit = shared compliance content, Total Loss, and company/billing. The tmfsql core (Claim/Assessment/Disposition/Company) exists in both.

3. The .NET APIs are the write layer. The Auto Liability, Scene, and Mobile APIs own the writes; the Next.js frontends and the RN app never touch the DB directly. The legacy ASP still writes directly — a migration risk to retire.

4. The investigation family (AutoInvestigator*) is the hub where web (assignment), scene (diagram), and mobile (identity/answers/files) converge — all keyed by AutoInvestigatorID + ToolkitID.

5. AI never queries claim data directly. ctk-mcp-nls reaches claims only through the .NET REST API + resolves prompts from AskCtk_Prompt*; AI-CTK-NLP reads compliance via a CSV export → FAISS. AI writes live only in Postgres/pgvector.

6. Big files live in S3, not SQL — scenes, evidence, ID scans, audio, PDFs. SQL holds only the metadata (AutoInvestigatorFiles, …SceneDiagramID).

🔎 Two things you asked about earlier: MultiCar lives in Facts.MultiCar + Assessment.MultiCar/MultiCarNotes (no "MultiVehicle"). Canada compliance links are tracked in the shared DB's ComplianceCanadaStatesBrokenLinksData, but the page content is still static (not in DBSummary).
