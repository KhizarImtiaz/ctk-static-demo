Overview

What Is AI-CTK-NLP?

AI-CTK-NLP is a compliance chart search API. Insurance adjusters type a plain-English question — the system automatically detects the state, searches thousands of compliance records using AI, and returns the most relevant legal chart references instantly.
Example in action

An adjuster asks: "What are the right of way laws in California for Auto claims?"

The API extracts California as the state, filters to Auto line of business, runs a semantic vector search, and returns 1 primary match (most relevant) + 5 secondary matches (related), each with a URL, chart name, category, and aliases.

Architecture

How Data Flows

Every search request goes through 6 stages before returning a result to the user.

1

User sends a question

Provides a plain-English question and a line of business (Auto, Commercial, or Homeowners). No need to know chart names or IDs.

2

State is extracted automatically

The API scans the question text using regex to detect a US state or Canadian province — by full name (California) or abbreviation (CA). If no state is found, a 400 Bad Request is returned immediately.

3

Semantic search on the FAISS index

The question is converted into a vector using the BGE embedding model. FAISS searches the local compliance chart index, filtered by the detected state and line of business. Returns the top 6 most semantically relevant records using Max Marginal Relevance — balancing relevance and diversity.

4

AI formats the results

The 6 FAISS records are sent to the Ollama Gemma2 27B model along with the original question. The LLM formats them into a structured response: 1 Primary (best match) + 5 Secondary (related matches), each with URL, chart name, category, and aliases.

5

Query is logged to PostgreSQL

The question and total response time are saved to the response_times table for performance monitoring and analytics.

6

Result returned to user

Full JSON response with the AI-formatted result, detected state info, and metadata (response time, model name, timestamp).

Streaming mode: The /search/stream endpoints follow the same flow but stream the AI output token-by-token as Server-Sent Events (SSE) — the UI can display results progressively without waiting for the full response.

FAISS Vector Index — Local Disk

Not a traditional database — a file-based vector index optimized for fast semantic search. Each record stores a compliance chart row as a high-dimensional vector alongside its metadata.

Vector Index

FAISS Index — How CRUD Works

FAISS has no SQL-style commands. There are no INSERT or UPDATE statements. Here is how each operation is performed:

Create — Build the Index

Triggered automatically at startup only if the index folder is missing.

  • Reads the compliance CSV file
  • Converts each row into a Document with text + metadata
  • BGE model embeds every document into a vector
  • FAISS builds the searchable index
  • Saves index to disk (server-ctk-embeddings-local/)

Automatic — one-time at startup

Read — Search the Index

Called on every search request.

  • User question is embedded into a vector
  • FAISS finds the top 6 closest vectors
  • Filtered by state_id + line_of_business_id
  • Uses Max Marginal Relevance to balance relevance and diversity in results

Automatic — every /search call

Update — Refresh the Data

No partial update exists in FAISS. A full rebuild is required.

  • Update the source CSV file with new data
  • Delete the server-ctk-embeddings-local/ folder
  • Restart the application
  • Startup detects missing folder → full rebuild

Manual — full rebuild required

Delete — Remove Records

No row-level delete exists in FAISS. Same approach as Update.

  • Remove the record from the CSV file
  • Delete the server-ctk-embeddings-local/ folder
  • Restart the application
  • Index rebuilds without the removed record

Manual — full rebuild required

Data Pipeline

CSV Data Source — Where It Comes From

The compliance data originates from the ClaimtoolKit SQL Server MainDB. Someone manually runs a query against the DB* compliance tables, exports the result to a CSV file, places it in the project folder, and restarts the app. This is a fully manual process.
Manual Update Steps
1

Query ClaimtoolKit SQL Server

Run a SELECT against the DB* compliance tables in the ClaimtoolKit MainDB to get all chart data.

2

Export result to a new CSV file

Name it with the current date — e.g. CTK_Updated_Database_june_16_2025.csv

3

Drop CSV into the project folder

Place the new file in CTK_csv_data/.

4

Update the hardcoded filename in app.py

Change the CSV path in app.py line ~202 to the new filename.

5

Delete the old FAISS index folder

Remove server-ctk-embeddings-local/ so startup triggers a rebuild.

6

Redeploy / Restart the app

App detects missing index → rebuilds from new CSV automatically → system is live with updated data.

Known Issues with the Current Process

1. Filename is hardcoded in app.py — every data update requires a code change + redeployment.

2. No automation — relies on someone manually remembering to export and deploy.

3. Old CSV files pile up — 5 files already exist with no cleanup process.

4. No staleness indicator — there is no way to know from the API how old the compliance data is.

Recommendation: The SQL Server connection (ctk_connection_sql.py) already exists in the project. The data pipeline could be automated to query the MainDB directly and rebuild the FAISS index on a schedule — eliminating the manual steps entirely.
