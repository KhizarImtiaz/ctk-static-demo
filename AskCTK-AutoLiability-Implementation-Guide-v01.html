Section 6
Resilience & Retry Logic
What happens when the AI server is down or returns an error. The system retries automatically with increasing delays, then marks the job as failed for manual review.
Retry Schedule
Job runs
↓ AI server error or timeout
Attempt 1 fails
→ wait 1 minute → Status: RETRY
↓ still failing
Attempt 2 fails
→ wait 5 minutes → Status: RETRY
↓ still failing
Attempt 3 fails
→ wait 15 minutes → Status: RETRY
↓ still failing (MaxRetryCount = 3 reached)
FAILED
Manual review required. Claim save was never affected.
⚠️
The adjuster's original save always succeeds regardless of retry status. A FAILED AI job means the AI summary field stays empty — not that the claim was lost.
Dedup Guard
Prevents duplicate AI jobs
Before inserting a new queue row, check: does a PENDING, PROCESSING, or RETRY job already exist for this exact combination of CompanyId + ToolkitId + SourceTable + SourceRecordId + AiRequestType?
If yes: skip the insert — return null (no new job)
If no: insert new PENDING job
This matters when adjusters type quickly and save multiple times in the 60-second debounce window — only one AI job runs, not one per keypress.
Debounce (NotBeforeAt)
Every new job is created with NotBeforeAt = now + 60 seconds.

This means if the adjuster saves at 10:00:00, the AI job won't be picked up until 10:01:00 at the earliest. If they save again at 10:00:30, the dedup guard skips the second job. The first job still runs once at 10:01:00 — reading the latest saved state at that point.

Section 8
The 5 Safety Rules
These rules must never be broken. They protect claim data integrity, adjuster productivity, and audit compliance.
Rule 1
AI NEVER Blocks the Save
The user's save operation MUST complete in under 1 second. AI processing happens in a separate background thread. If the AI server is down, the adjuster's save still works perfectly — the AI job just waits in the queue.
Rule 2
Enqueue is Atomic with Save
The Facts write and the AI queue insert happen in the SAME database transaction. If the save fails (e.g., validation error), the queue insert is also rolled back — no orphan jobs are ever created for claims that weren't actually saved.
Rule 3
AI Writes Only to Designated Columns
AI cannot write to any arbitrary field. Every AI function has a specific Writer class that targets only a pre-approved set of columns. Adding a new AI output target requires adding a new Writer class — not changing the AI call itself.
Rule 4
Every AI Write is Audited
Every job lifecycle event (STARTED, COMPLETED, FAILED, RETRY) writes a row to AskCtk_AuditLog. This provides a complete history of what AI wrote, when, for which claim, and from which prompt version — essential for claims disputes and compliance review.
Rule 5
Worker Sets Tenant Context First
The background worker has no HTTP request — so there is no automatic tenant resolution. Before reading or writing any claim data, the worker MUST call HttpTenantProvider.SetTenantId(job.CompanyId). Without this, the DB context doesn't know which company's database to use.
✅
What this means for the adjuster: They fill in the party statement, click Save, and immediately continue their work. 30–60 seconds later, when they revisit the statement, the AI summary badge has appeared automatically — with a structured analysis of what was said, what's missing, and any contradictions. No waiting, no manual requests, no extra clicks.
